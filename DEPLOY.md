# Hosting Coin Audit online

**Use Render** (I read "onder" as Render). Vercel cannot run this bot's engine properly — details in [Why not Vercel](#why-not-vercel).
After the steps below you have a private website at `https://<your-service>.onrender.com`: you log in, type a coin,
pick a timeframe, and get the same report the desktop version makes. It also re-audits your watchlist after every
candle close, grades past signals, and can push approved signals to Discord or Telegram.

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/Minhasokz2/trading-bot)

The button (or **New + → Blueprint** in the Render dashboard) reads [`render.yaml`](render.yaml) from this repository.
This repository is public, so put **no secrets in it**: the password is generated by Render and alert URLs are set in
Render's Environment tab.

---

## 1. What it needs (measured, not guessed)

| Item | Measured value | Consequence |
|---|---|---|
| One audit, all 27 strategies + ML, 3000 candles | ≈ **500 MB** peak memory, ≈ 12 s of CPU (single-threaded) | A 512 MB plan runs out of memory. The blueprint uses **Standard (2 GB RAM, 1 CPU)**. |
| The web server on its own | ≈ 55 MB | Fine next to a running audit. |
| Python packages in the image | ≈ 630 MB (3.11) / 680 MB (3.12) installed | Image is roughly 1 GB; first build takes several minutes. |
| Data written per audit | a few hundred KB (report + JSON) | 5 GB disk is plenty; reports older than 14 days are pruned (the newest per coin is always kept). |

Not measured here: how long the **first** audit of a coin takes to download candles from Binance (this sandbox cannot reach
Binance). Later audits use a cached copy on the disk and only fetch new candles.

Render sells Standard at about $25 per month, Starter at $7, and the disk is billed per GB on top (search snapshot; check the
[pricing page](https://render.com/pricing)). A service with a disk needs a paid plan.

## 2. Deploy on Render (about 10 minutes)

1. **Account.** Sign up at render.com and add a payment method. Connect GitHub if Render asks (the repo is public, so this
   is only needed for auto-deploys).
2. **Create the service.** Click the *Deploy to Render* button above, or **New + → Blueprint**, pick
   `Minhasokz2/trading-bot`. The default branch is `claude/binance-audit-bot-review-ms60mc`, which contains everything.
   Render shows one service, **coin-audit**: Docker, Standard, **Frankfurt**, 5 GB disk mounted at `/data`. Click **Apply**.
3. **Wait for the build.** *Logs* shows the image build (several minutes the first time). The service is live when the
   status says *Live*.
4. **Get the password.** Service → **Environment** → `COIN_AUDIT_PASSWORD` → reveal. The user name is `admin`.
5. **Open the site** (the `onrender.com` link at the top of the service page) and log in.
6. **Check the region first.** Click **Connectivity**. *Binance Spot market data* must say ✔ ok.
   If it says **HTTP 451 / blocked**, Binance refuses that region. A Render service's region **cannot be changed**:
   delete the service, change `region:` in `render.yaml` to `singapore` (or `frankfurt`), and deploy again.
7. **Prove the engine works.** Click **Demo check (synthetic data)**. It finishes in about 15 seconds and needs no internet.
   Open the report it lists.
8. **Run a real audit.** Type `SOL`, timeframe `4h`, **Run audit**. Watch the log; the report link appears when it ends.
9. **Optional alerts** — Environment tab → *Add Environment Variable*, then save (Render redeploys):

   | To get alerts in… | Add |
   |---|---|
   | Discord | `DISCORD_WEBHOOK_URL` = the channel webhook (Channel settings → Integrations → Webhooks) |
   | Telegram | `TELEGRAM_BOT_TOKEN` (from @BotFather) and `TELEGRAM_CHAT_ID` |

   Scheduled runs then send a message when the verdict is FAVORABLE; the *Send alert* box on the forms does the same on demand.

**Verify from your own computer** (needs `bash`, `curl`, `python3`):

```bash
REQUIRE_BINANCE=1 docker/smoke_test.sh https://<your-service>.onrender.com <the-password>
```

It checks the health endpoint, the login wall, a wrong password, data-source reachability and a full demo audit.

### Creating the service by hand instead of the Blueprint

New + → **Web Service** → *Build and deploy from a Git repository* → this repo → **Language: Docker**. Then set:
Region **Frankfurt** or **Singapore**, Instance type **Standard**, Health Check Path `/healthz`, a **Disk** named
`coin-audit-data` mounted at `/data` (5 GB), and the environment variables in the table below.

## 3. Settings (environment variables)

| Variable | Default | Meaning |
|---|---|---|
| `COIN_AUDIT_PASSWORD` | generated by Render | Login password. **Without it every page returns 503** (a locked site, never an open one). |
| `COIN_AUDIT_USER` | `admin` | Login name. |
| `COIN_AUDIT_DATA_DIR` | `/data` | Reports, logs, candle caches, job history, live track record. Must be the disk's mount path. |
| `COIN_AUDIT_TRUST_PROXY` | `1` | Take the client address from a proxy header (needed behind Render for the failed-login throttle). |
| `COIN_AUDIT_CLIENT_IP_HEADER` | `true-client-ip` | Which header carries the real client address. Render sits behind Cloudflare, so the socket address is shared; Render sets `True-Client-IP`. |
| `COIN_AUDIT_WATCHLIST` | `BTC,ETH,SOL` | Coins re-audited after every candle close. Empty = nothing scheduled. Up to 10. |
| `COIN_AUDIT_WATCH_TF` | `4h` | `15m`, `1h`, `4h`, `1d`. |
| `COIN_AUDIT_SCHEDULE_ML` | `0` | `1` turns the ML meta-labeler on for scheduled runs (slower). |
| `COIN_AUDIT_SCAN_HOURS` | `0` (off) | Run a market scan every N hours; `COIN_AUDIT_SCAN_N` (default 20) and `COIN_AUDIT_SCAN_TF` (default `4h`) shape it. |
| `COIN_AUDIT_REVIEW_HOURS` | `24` | Grade past signals and refresh the live track record; `0` = off. |
| `COIN_AUDIT_KEEP_DAYS` | `14` | Report retention. |
| `COIN_AUDIT_MAX_JOBS` | `1` | Audits running at once. Each needs ≈ 500 MB, so raise it only together with the instance size. |
| `COIN_AUDIT_ALLOWED_ORIGINS` | – | Extra origins allowed to POST (only needed if you put another proxy or domain in front). |
| `DISCORD_WEBHOOK_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | – | Alerts. Treat them as secrets. |

More tuning (fees, gates, risk caps, verdict thresholds): copy `audit/settings.toml` to `/data/settings.toml` and edit it
(Render's *Shell* tab); the copy on the disk wins. Same for your event calendar: `/data/events.csv`.

## 4. Security

* Everything except `/healthz` sits behind HTTP Basic login over HTTPS (Render terminates TLS). Passwords are compared
  in constant time; 8 wrong passwords from one address lock it out for 10 minutes. The throttle is best effort (it keys on
  Render's `True-Client-IP`); the real protection is the long random password Render generates.
* Every POST must come from this site's own pages (checked with the browser's `Sec-Fetch-Site` header, with `Origin` as the fallback), because browsers attach Basic credentials to cross-site form posts.
* Pages carry a strict Content-Security-Policy: scripts only from `/static/` plus one hashed theme snippet, no inline
  handlers. Raw HTML inside a report is shown as text. Stored chart pages are re-rendered from the report's JSON with the
  current renderer; the HTML tearsheet runs sandboxed.
* File access is by exact report name only; `..`, slashes and hidden files are refused.
* There are **no exchange API keys anywhere**, and nothing in this project can place an order.
* The container runs as an unprivileged user. It starts as root only long enough to fix the disk's ownership, then drops privileges.
* Rotate the password by editing `COIN_AUDIT_PASSWORD` (Render redeploys). Use a long random one.

## 5. Running it

* **Deploys take a few seconds of downtime**: a service with a disk stops the old instance before starting the new one
  ([Render disks](https://render.com/docs/disks)). A job in flight is marked *interrupted*; jobs still waiting resume.
* **One instance only.** A disk cannot be shared or scaled out, which is fine for this workload.
* **Reading a result.** A finished job links to its report page: a summary card (verdict, plan, signals, a re-run button),
  the chart with the plan drawn on the candles, then the full report. *Reports* lists every audit with verdict and score;
  *Dashboard* shows the latest audit per coin.
* **Backups.** Render snapshots the disk every 24 hours and keeps them for at least 7 days (full-disk restore only).
* **Memory kills.** If a job ends as *failed — killed, most likely out of memory*, use the next plan up or narrow the job
  with the *Only these strategies* box.
* **Free plan won't work**: no persistent disk, 512 MB of RAM, and it sleeps when idle, which would stop the scheduler.
* **Not included online**: the Freqtrade dry-run bots (`freqtrade/`, run locally with Docker) and
  `research/verdict_backtest.py` (run locally; it needs your own copy of the data).

### Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Page says "Coin Audit is running but has no login password" | `COIN_AUDIT_PASSWORD` is empty. Set it in Environment. |
| Login prompt loops | Wrong user or password. The user is `admin` unless you changed `COIN_AUDIT_USER`. |
| "Too many wrong passwords" | Wait ten minutes. |
| Job failed: *Binance refused this server's region (HTTP 451)* | Wrong region. Recreate the service in Frankfurt or Singapore. |
| Job failed: *Could not reach Binance* | Open **Connectivity** for the per-source result. |
| Job failed: *killed — most likely out of memory* | Bigger plan, or narrow the job. |
| Home page banner "Less than 200 MB of disk left" | Raise the disk size in Render (it can only grow) or lower `COIN_AUDIT_KEEP_DAYS`. |
| Deploy stuck on "health check failed" | Health Check Path must be `/healthz`, and the app must listen on Render's `PORT` (it does by default). |
| Scheduled jobs never run | `COIN_AUDIT_WATCHLIST` is empty, or the previous run of that schedule is still going (a schedule never overlaps itself). |

## Why not Vercel

Vercel runs short-lived, stateless functions. This bot is a Python data-science engine with a scheduler and files that must
persist. What the current Vercel documentation says, next to what this app needs:

| | Vercel Functions (Python) | This app |
|---|---|---|
| Package size | 500 MB uncompressed (raised from 250 MB); "large functions" go up to 5 GB but need fluid compute | 630–680 MB installed |
| Run time | 300 s (Hobby), 800 s (Pro; 1800 s in beta) per invocation | one audit ≈ 15–60 s, but a 40-coin scan or the watch loop runs for many minutes or indefinitely |
| Disk | read-only, with a 500 MB temporary `/tmp` per instance | reports, logs, candle cache, job history and the live track record must persist |
| Background work | none between requests (a cron entry can only call an endpoint on a timer) | job queue and candle-close scheduler |
| Region | defaults to a US region unless you set one | Binance refuses the US (HTTP 451) |

It could be forced to work only by rewriting the storage layer onto an external database or blob store, splitting scans
into invocations shorter than the limit, and moving the scheduler onto cron calls. That is a different program, and it
would still lack a place to run `--loop`. Vercel *is* a fine home for a thin front-end that calls this service's
`/api/*` endpoints, but the site above already has its own interface, so there is nothing to gain today.

Sources: [Python bundle limit raised to 500 MB](https://vercel.com/changelog/python-vercel-functions-bundle-size-limit-increased-to-500mb),
[Vercel Functions limits](https://vercel.com/docs/functions/limitations),
[Vercel Python runtime](https://vercel.com/docs/functions/runtimes/python).
Render: [Blueprint reference](https://render.com/docs/blueprint-spec), [Persistent disks](https://render.com/docs/disks).

## Other hosts, or your own machine

The image is plain Docker, so anything that runs a container and gives it a persistent volume works (Fly.io, Railway, a VPS).

```bash
docker build -t coin-audit .
docker run -d --name coin-audit -p 10000:10000 -e COIN_AUDIT_PASSWORD=choose-a-long-one -v coinaudit:/data coin-audit
docker/smoke_test.sh http://localhost:10000 choose-a-long-one
```

Without Docker: `./linux/serve.sh` (Windows `SERVE.bat`, macOS `mac/12 Web app.command`) starts the same site on
`http://127.0.0.1:10000` from your local install.
